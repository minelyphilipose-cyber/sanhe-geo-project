# 合伙人协作交付业务规划 v1

日期: 2026-06-30

## 1. 定位

当前系统仍以总部内部交付为主导。合伙人进入系统后,负责客户、品牌、项目、核心问题等交付前置信息的录入和维护,并可生成售前诊断报告辅助成交;总部负责项目准入审核、积分消耗确认、内部交付人员指派、账号和指纹浏览器环境配置、内容分发和正式启动。

本期目标不是开放客户自助交付,而是建立“合伙人提交资料和项目申请,总部审核并接管交付”的协作闭环。

## 2. 角色模型

### 2.1 总部角色

| 角色 | 主要职责 |
| --- | --- |
| 超级管理员 | 全局配置、用户权限、合伙人、套餐、积分、全部数据 |
| 管理者 | 全局业务管理和数据查看 |
| 交付负责人 | 审核合伙人项目启动申请,指派内部交付人员,管理交付准备 |
| 内部交付人员 | 处理账号绑定、指纹浏览器、行业资讯站、平台网站、自媒体环境和正式启动 |
| 销售 | 售前诊断、客户信息查看,不处理合伙人积分和项目审批 |

总部角色中,只有具备交付负责人权限的账号可以审批合伙人项目启动申请。

### 2.2 合伙人角色

| 角色 | 主要职责 | 限制 |
| --- | --- | --- |
| 合伙人负责人 | 创建和维护客户、品牌、项目、核心问题;生成诊断报告;提交项目启动申请;查看积分;创建一个交付员工;重置员工密码 | 不能看到内容、指纹浏览器、自媒体账号绑定和总部隐藏渠道 |
| 合伙人交付员工 | 维护被分配客户/项目的资料、品牌和核心问题 | 不能看诊断报告、不能提交启动申请、不能编辑项目配额、不能看积分 |

每个合伙人当前只能创建一个合伙人交付员工。合伙人负责人停用后,其员工同步停用;负责人重新启用时,员工不自动恢复,由总部或负责人手动启用。

现有 `partner_viewer` 从新版本角色体系移除,不再作为合伙人门户目标角色。

当前已确认没有 `partner_viewer` 历史账号。本期不做账号转换流程;迁移脚本需要增加前置校验,如果发现存量 `partner_viewer` 用户则阻断迁移并要求人工确认。

## 3. 数据可见边界

### 3.1 合伙人负责人

- 只能看到自己 `partner_id` 下的数据。
- 可见本合伙人的客户、品牌、项目、核心问题、诊断报告、积分流水。
- 可见合伙人套餐中对合伙人开放展示的部分。
- 不可见总部直营客户、其他合伙人客户、内容执行、指纹浏览器、本地助手、自媒体账号绑定、隐藏渠道。

### 3.2 合伙人交付员工

- 只能看到负责人分配给自己的客户。
- 可见这些客户下的品牌、项目和核心问题维护入口。
- 不可见诊断报告、积分、套餐商业配置、内容和总部交付配置。

### 3.3 总部

- 按总部角色和权限查看直营及所有合伙人数据。
- 可查看完整合伙人套餐配置,包括合伙人不可见的隐藏渠道。
- 可查看项目审批通过时保存的套餐、折扣、积分和配额快照。

## 4. 合伙人套餐

### 4.1 基本规则

- 套餐绑定在客户维度,项目不绑定套餐。
- 合伙人创建项目前,客户必须已绑定合伙人套餐,否则无法分配项目配额。
- 总部套餐和合伙人套餐分离。
- 所有合伙人共用一套合伙人套餐池。
- 合伙人套餐需要上下架状态。
- 合伙人套餐未被客户绑定时可删除;一旦被任意客户绑定,禁止删除,只能停用/下架。
- 停用/下架套餐不允许新客户绑定,历史客户继续保留套餐快照。
- 套餐创建后不做原地变更;如果套餐策略变化,通过新增套餐承接。
- 套餐编辑接口只能编辑草稿态套餐;已上架或已被绑定的套餐不允许通过 `PUT` 原地修改核心配置。
- 首单积分消耗前,合伙人负责人可以修改客户绑定套餐。
- 首单积分消耗后,客户套餐锁定,总部也不做套餐变更。

### 4.2 展示边界

合伙人套餐内部可配置完整交付能力,包括:

- Agent 官网。
- 自媒体平台。
- 论坛/平台网站。
- 行业资讯站。
- 权威媒体。
- 其他总部内部交付资源。

Agent 官网属于合伙人可见渠道,不属于隐藏渠道。隐藏渠道额度对合伙人零感知,但需要进入总部内部交付快照。对于一个客户下的多个项目,合伙人套餐配置的隐藏渠道额度对每一个项目都相同,不从客户总额度中递减分摊。

配额在产品和接口上分为两层:

- `partner_allocated_quota`: 合伙人可见、可分配、参与客户套餐剩余额度递减。
- `internal_delivery_snapshot`: 合伙人不可见,由套餐内部配置生成,不参与客户套餐剩余额度递减,每个审批通过项目保存同额内部快照。

`partner_allocated_quota` 包含 Agent 官网、自媒体平台和核心问题;`internal_delivery_snapshot` 包含论坛/平台网站、行业资讯站、权威媒体等总部隐藏交付渠道。

合伙人侧只展示:

- Agent 官网数量与频次。
- 公众号数量与频次。
- 抖音数量与频次。
- 头条数量与频次。
- 知乎数量与频次。
- 百家号数量与频次。
- 小红书数量与频次。
- 核心问题数量。

合伙人侧不展示:

- B/C 类问题。
- 论坛/平台网站。
- 行业资讯站。
- 权威媒体。
- 隐藏渠道数量与频次。
- 总部内部执行方式。

### 4.3 快照

客户套餐锁定后,后台允许查看历史套餐快照。项目审批通过时必须保存:

- 客户绑定套餐快照。
- 合伙人可见套餐配置快照。
- 总部内部完整套餐配置快照。
- 合伙人折扣系数快照。
- 本次消耗积分快照。
- 项目配额快照。

快照用于后续交付和审计,不受套餐后续上下架或配置变化影响。

## 5. 积分体系

### 5.1 基本规则

- 数据库可沿用账户与流水模型,产品文案统一叫“积分”。
- 合伙人创建时手动录入初始积分。
- 初始积分、人工增加、人工扣减都必须填写原因并上传凭证。
- 合伙人可在自己的积分页面查看积分流水。
- 总部管理员可以处理合伙人积分。

### 5.2 消耗规则

- 积分消耗发生在总部审核通过合伙人项目时。
- 仅客户下第一个“审核通过并进入总部处理”的项目触发首单积分消耗。
- 驳回不计首单。
- 首期不自动处理客户合并、迁移、跨合伙人转移等复杂场景。
- 消耗积分 = 客户绑定套餐积分 x 合伙人折扣系数。
- 折扣系数 `0.8` 表示八折。

### 5.3 校验规则

合伙人负责人提交项目启动申请时:

- 如果该项目可能成为客户首单,系统先校验积分是否充足。
- 积分不足时拒绝提交启动申请并提示。
- 总部审批通过前再次校验积分。
- 审批通过时正式写入积分消耗流水。

### 5.4 撤销限制

- 只有项目审批通过前,合伙人负责人可以撤销启动申请。
- 审批通过后,合伙人不允许撤销。
- 总部不做主动撤销。
- 审批通过即发生积分消耗;审批通过后不进入返还流程。
- 正式启动后不允许合伙人申请撤销。

## 6. 客户链路

1. 合伙人负责人创建客户。
2. 客户必须绑定合伙人套餐后,才允许创建项目。
3. 首单消耗前,合伙人负责人可以修改客户套餐。
4. 首单消耗后,客户套餐锁定。
5. 总部审批首个项目通过时,审批人必须把客户分配给指定内部交付人员。
6. 一个客户多个项目后续自动归同一内部交付人员。
7. 合伙人负责人可把客户分配给自己的合伙人交付员工。
8. 合伙人交付员工只能看被分配客户和这些客户下的项目。

## 7. 品牌链路

合伙人可维护品牌基础资料:

- 品牌名称。
- 业务介绍。
- 服务区域。
- 官网和联系方式。
- 标准品牌表述。
- 禁用词。
- 品牌素材。
- 文件封面文件夹。
- 插图文件夹。

项目审批通过或正式启动后:

- 文件封面文件夹、插图文件夹仍允许调整。
- 指纹浏览器、自媒体账号、登录态、Cookie、浏览器环境仍只对总部开放。
- 行业资讯站由总部内部交付人员配置,合伙人不可见。

## 8. 项目与配额

### 8.1 项目创建

- 合伙人负责人可以创建项目。
- 合伙人交付员工可以维护被分配项目资料。
- 合伙人交付员工不能编辑项目配额。
- 合伙人交付员工不能提交启动申请。
- 项目不绑定套餐。
- 项目配额来自客户绑定套餐的剩余可用额度。
- 创建项目时默认分配客户套餐全部剩余可用额度。
- 合伙人负责人可以手动调整本项目配额。
- 分配不能超过客户套餐剩余额度。
- 草稿中的配额只是草稿值,不占用客户套餐额度。提交启动申请时必须按实时剩余额度重新校验,若草稿配额超过实时剩余,拒绝提交并要求重新分配。

### 8.2 配额锁定与释放

| 场景 | 配额处理 |
| --- | --- |
| 项目草稿 | 可编辑,不占用客户套餐剩余额度 |
| 提交启动申请 | 开始占用额度,项目配额锁定 |
| 总部驳回 | 释放额度并解锁,可修改后重新提交 |
| 审批前删除/撤销申请 | 不占用或释放额度 |
| 审批通过 | 永久锁定并保存快照 |
| 正式启动 | 按审批快照执行 |

### 8.3 核心问题

- A 类问题在合伙人侧展示为“核心问题”。
- 若项目绑定客户套餐中没有 B/C 类问题,拓词页面不展示任何 B/C 元素。
- 合伙人只做核心问题生成与维护。
- 项目启动后,拓词不能修改。

## 9. 项目状态机

### 9.1 状态定义

本期合伙人项目列表、详情、统计、工作台统一返回 `projectDisplayStatus`。`projectDisplayStatus` 是对外展示和筛选的唯一状态口径。

权威来源:

- 合伙人新流程项目: 由 `project.status` 与最新 `project_start_request.status` 派生 `projectDisplayStatus`。
- 正式启动后的项目: 以 `project.status` 为主。
- 旧项目/总部直营项目: 通过旧状态映射表派生 `projectDisplayStatus`。

研发阶段必须保证列表、详情、统计、导出、工作台使用同一套状态解析器,禁止各页面自行判断。

| 状态 | 含义 | 合伙人可见文案 |
| --- | --- | --- |
| `draft` | 草稿,可编辑 | 待提交 |
| `submitted` | 已提交启动申请,等待总部审核 | 审核中 |
| `rejected` | 总部驳回,可修改后重新提交 | 已驳回 |
| `approved_pending_setup` | 总部审核通过,积分已消耗,客户已指派内部交付人员,等待总部配置 | 总部配置中 |
| `setup_ready` | 总部账号和环境准备完成,可正式启动 | 待启动 |
| `active` | 总部正式启动项目 | 交付中 |
| `paused` | 暂停 | 已暂停 |
| `completed` | 完成 | 已完成 |
| `archived` | 归档 | 已归档 |
| `cancelled` | 项目取消预留状态,本期不实现入口 | 已取消 |

### 9.2 自动流转

| 动作 | 起始状态 | 目标状态 | 操作者 |
| --- | --- | --- | --- |
| 创建项目 | - | `draft` | 合伙人负责人 |
| 提交启动申请 | `draft` / `rejected` | `submitted` | 合伙人负责人 |
| 审核驳回 | `submitted` | `rejected` | 总部交付负责人 |
| 审核通过 | `submitted` | `approved_pending_setup` | 总部交付负责人 |
| 总部配置完成 | `approved_pending_setup` | `setup_ready` | 内部交付人员 / 交付负责人 |
| 正式启动 | `setup_ready` | `active` | 内部交付人员 / 交付负责人 |
| 暂停 | `active` | `paused` | 总部 |
| 恢复 | `paused` | `active` | 总部 |
| 完成 | `active` | `completed` | 总部 |
| 归档 | `completed` | `archived` | 总部 |
| 撤销启动申请 | `submitted` | `draft` | 合伙人负责人 |

撤销启动申请只取消申请,不取消项目本身。撤销后释放申请占用额度,项目回到可编辑草稿状态。项目审核通过后,合伙人不允许撤销。总部不做主动撤销。

`cancelled` 为项目取消预留状态,本期不提供任何入口进入该状态;本期取消语义只存在于启动申请状态。

### 9.3 旧状态映射

| 数据范围 | 旧状态/条件 | `projectDisplayStatus` | 说明 |
| --- | --- | --- | --- |
| 合伙人项目 | `pending_start` 且无启动申请 | `draft` | 视为待提交资料 |
| 合伙人项目 | 最新启动申请 `submitted` | `submitted` | 审核中 |
| 合伙人项目 | 最新启动申请 `rejected` | `rejected` | 可修改后重提 |
| 合伙人项目 | 最新启动申请 `cancelled` 且项目未审批通过 | `draft` | 取消申请不取消项目 |
| 合伙人项目 | 最新启动申请 `approved` 且项目未 `active` | `approved_pending_setup` | 已审批,总部配置中 |
| 合伙人项目 | `active` | `active` | 正式交付中 |
| 合伙人项目 | `paused` | `paused` | 暂停 |
| 合伙人项目 | `expired` | `archived` | 旧到期项目按归档展示 |
| 总部直营项目 | `pending_start` | `draft` 或内部旧文案 | 首期可兼容旧文案,但接口需给统一 display status |
| 总部直营项目 | `active` | `active` | 正式交付中 |
| 总部直营项目 | `paused` | `paused` | 暂停 |
| 总部直营项目 | `expired` | `archived` | 归档展示 |

如发现历史合伙人项目已有积分/余额扣减流水但未有启动申请,迁移阶段应进入人工核验清单,不得自动推断为已审批。

## 10. 项目启动申请

### 10.1 提交前校验

合伙人负责人提交启动申请时,系统自动校验:

- 当前用户是合伙人负责人。
- 客户属于当前合伙人。
- 客户已绑定合伙人套餐。
- 客户套餐未被非法修改。
- 项目资料完整。
- 项目配额合法。
- 项目配额未超过提交时实时剩余额度。
- 项目当前状态允许提交。
- 若项目可能成为客户首单,合伙人积分充足。

### 10.2 总部审核

总部审核只允许:

- 同意。
- 否决。

总部不代合伙人修改套餐和项目配额。

同意时系统自动:

- 再次校验积分。
- 判断是否客户首单。
- 如为首单,消耗积分并写流水。
- 锁定客户套餐。
- 锁定项目配额。
- 保存套餐、折扣、积分、配额快照。
- 若客户尚未分配内部交付人员,要求审批人选择内部交付人员。
- 若客户已有内部交付人员且账号有效,自动沿用原内部交付人员。
- 若客户已有内部交付人员但账号已停用,要求先走客户移交流程后才能审批通过。
- 项目进入 `approved_pending_setup`。

否决时系统要求:

- 选择结构化驳回原因。
- 可填写补充说明。
- 项目进入 `rejected`。
- 项目资料与配额重新允许合伙人负责人修改。

建议驳回原因:

- 客户资料不完整。
- 品牌资料不完整。
- 项目需求不清。
- 套餐配额不合理。
- 积分不足。
- 行业不适配。
- 资料真实性存疑。
- 其他。

## 11. 总部交付准备

`approved_pending_setup` 阶段由总部内部交付人员处理:

- 自媒体账号绑定。
- 指纹浏览器环境配置。
- 浏览器账号登录态确认。
- 插件和本地助手准备。
- Agent 官网配置。
- 行业资讯站配置。
- 平台网站/论坛配置。
- 权威媒体配置。
- 内部交付检查。

这些内容合伙人不可见。准备完成后,内部交付人员或交付负责人将项目流转到 `setup_ready`,再由总部正式启动为 `active`。

### 11.1 客户移交

客户分配是客户级归属。若客户已有内部交付人员,后续项目默认沿用该负责人。

当原内部交付人员账号被停用、离职或不再负责该客户时,需要通过总部客户移交流程处理:

- 入口: 总部客户详情、合伙人项目审批页的阻断提示、总部交付准备看板。
- 操作者: 拥有 `delivery.assignment.manage` 权限的总部用户。本期默认交付负责人和超级管理员可操作;如管理者也需要移交,必须同步调整权限种子和断言。
- 动作: 选择新的内部交付人员,填写移交原因。
- 结果: 更新客户内部交付负责人,后续该客户所有项目默认归新负责人。
- 审计: 记录原负责人、新负责人、操作人、原因、时间。

## 12. 诊断报告

- 诊断报告可在客户建档前生成。
- 合伙人负责人生成诊断报告时,只绑定 `partner_id`。
- 合伙人负责人可查看自己 `partner_id` 下的全部诊断报告。
- 合伙人交付员工不可查看诊断报告。
- 总部管理员可查看全部合伙人诊断报告。
- 总部其他角色按权限控制。
- 合伙人管理中需要配置诊断报告免费次数和超额消耗积分规则。
- 合伙人生成诊断报告时,系统先扣减免费次数;免费次数不足时,按配置消耗积分。
- 若免费次数不足且积分不足,拒绝生成并提示。
- 诊断报告生成失败时,若已经扣减免费次数或积分,需要按失败原因执行回补或标记人工处理。

### 12.1 诊断报告次数与积分

合伙人诊断报告限制建议包含:

- `presale_report_free_quota`: 免费诊断次数。
- `presale_report_used_quota`: 已使用免费次数。
- `presale_report_extra_points`: 超额单次消耗积分。
- `presale_report_quota_reset_policy`: 是否重置,首期可固定为不自动重置。

生成流程:

1. 合伙人负责人发起诊断报告。
2. 系统校验 `partner_id` 和负责人权限。
3. 若剩余免费次数大于 0,预占一次免费次数。
4. 若免费次数不足,校验积分是否足够并预占超额积分。
5. 创建诊断报告并绑定 `partner_id`。
6. 生成成功后确认次数/积分消耗。
7. 生成失败时按失败类型自动回补或进入人工异常处理。

异常处理:

- 参数校验失败: 不扣次数和积分。
- 任务未创建成功: 不扣次数和积分。
- 任务创建后系统内部失败: 自动回补次数或积分。
- LLM/平台不可用导致失败: 自动回补次数或积分。
- 用户主动放弃或重复提交导致的失败: 不自动回补,进入人工处理。

### 12.2 诊断报告幂等与预占流转

诊断报告创建必须支持幂等,避免重复扣次数或积分。

幂等规则:

- 创建接口必须传入 `request_id`。
- `partner_id + request_id` 唯一。
- 相同 `request_id` 重复提交时,若已有报告任务,返回已有任务结果或当前状态,不得重复扣次数或积分。
- 如果请求参数与首次请求不一致,返回幂等冲突错误。

预占流水状态:

| 场景 | 原状态 | 目标状态 | 次数/积分处理 |
| --- | --- | --- | --- |
| 创建任务成功并进入生成 | - | `reserved` | 预占免费次数或积分 |
| 报告生成成功 | `reserved` | `confirmed` | 确认消耗 |
| 参数校验失败 | - | - | 不创建预占流水 |
| 任务未创建成功 | - | - | 不创建预占流水 |
| 系统内部失败 | `reserved` | `refunded` | 自动回补 |
| LLM/平台不可用失败 | `reserved` | `refunded` | 自动回补 |
| 生成超时 | `reserved` | `manual_review` | 继续冻结,人工确认成功或回补 |
| 用户主动取消 | `reserved` | `manual_review` | 继续冻结,人工判断是否回补 |
| 人工重跑 | `manual_review` 或 `refunded` | 按重跑结果确认 | 不得重复预占,需关联原流水 |

`manual_review` 状态下,额度或积分保持冻结,直到人工确认为 `confirmed` 或 `refunded`。

## 19. 当前实现差距与改造原则

本规划需要基于现有实现增量改造,不建议推翻重写。以下差距需要在研发方案中优先处理。

### 19.1 项目状态机方向相反

当前项目状态主要是 `pending_start` / `active` / `paused` / `expired`,创建项目会直接进入 `pending_start`。现有启动守卫还存在“合伙人负责人可直接启动合伙人项目、内部用户反而不能启动合伙人项目”的逻辑,这与目标流程相反。

当前数据库迁移中还存在项目状态触发器/约束,只允许 `pending_start` / `active` / `paused` / `expired`。因此状态机不是纯服务层改造,必须纳入数据库迁移。

目标改造:

- 合伙人不能直接启动项目。
- 合伙人只能提交启动申请。
- 总部交付负责人审核通过后进入 `approved_pending_setup`。
- 总部内部完成账号和环境配置后进入 `setup_ready`。
- 总部正式启动后进入 `active`。

建议实现上保留旧状态兼容读取,但新增项目启动申请/审批表驱动合伙人项目的新状态视图,逐步把合伙人项目迁移到新流程。

阶段一必须包含:

- 新增 Flyway 迁移,更新项目状态触发器/约束。
- 更新项目状态字典。
- 更新 `ProjectFlowPolicy`。
- 更新所有依赖 `pending_start` / `active` / `paused` / `expired` 的统计、工作台、筛选和导出逻辑。
- 明确旧项目状态到新状态的兼容映射。

### 19.2 合伙人员工数据边界未实现

当前 `partner`、`partner_staff`、`partner_viewer` 基本都按同一个 `partner_id` 做数据隔离,无法满足“合伙人交付员工只能看负责人分配给自己的客户/项目”。

目标改造:

- 新版本角色体系移除 `partner_viewer`,不再作为合伙人门户目标角色。
- 增加客户级合伙人员工分配字段或关系,首期可用 `company.partner_staff_owner_id`。
- 客户、品牌、项目、核心问题、拓词相关查询统一追加员工范围过滤。
- 合伙人负责人仍可看本合伙人全部数据。
- 合伙人交付员工只能看被分配客户及其下游数据。

`partner_viewer` 迁移任务:

- 前端合伙人路由不再允许 `partner_viewer` 进入。
- 后端 `CurrentUserService`、数据范围服务和权限种子不再把 `partner_viewer` 当作合伙人门户角色。
- 用户管理不再允许新建或分配 `partner_viewer`。
- 当前确认没有历史 `partner_viewer` 账号;迁移脚本需校验不存在存量账号。
- 如发现存量 `partner_viewer` 账号,迁移阻断并人工确认。
- 移除或废弃 `partner_viewer` 的角色授权。

### 19.3 套餐和客户绑定快照

当前套餐为统一 `package_plan`,客户绑定可复用 `company_package_binding`。业务已确认“套餐创建后不做原地变更,变更通过新增套餐”,历史锁定风险降低,但仍需要审批快照用于审计和交付执行。

目标改造:

- 在套餐层区分总部套餐和合伙人套餐。
- 合伙人套餐增加上下架状态和删除限制。
- 客户绑定合伙人套餐后,首单消耗前可改;首单消耗后锁定。
- 审批通过时保存套餐快照、合伙人可见配置快照、总部内部配置快照、折扣快照、积分消耗快照。

### 19.4 项目配额占用规则需调整

当前项目渠道配额主要统计 `active` 项目。目标规则调整为:

- 草稿不占用额度。
- 合伙人提交启动申请后开始占用额度。
- 驳回、审批前删除或合伙人撤销启动申请时释放额度。
- 审批通过后永久锁定项目配额并保存快照。
- 隐藏渠道配额不由合伙人分配,但审批通过时需要按套餐内部配置保存每项目同额内部快照。Agent 官网不是隐藏渠道,应归入合伙人可见配额。

可复用现有 `project_channel_allocation`,但需要增加分配状态、申请关联、锁定时间和快照,或新增项目配额表承接新语义。

### 19.5 积分和审批尚未绑定

当前合伙人账户和流水模型可复用,但仍是余额/充值/人工调整语义,缺少凭证、审批关联和首单消耗规则。

目标改造:

- 产品文案改为积分。
- 初始积分和人工调整必须有原因与凭证。
- 提交启动申请时做积分预校验。
- 总部审批通过时按 `套餐积分 x 折扣系数` 正式消耗。
- 消耗流水关联项目、客户、审批申请和套餐快照。
- 合伙人诊断报告也需要接入次数和超额积分消耗逻辑。

### 19.6 合伙人接口必须使用专用 DTO

当前渠道定义包含官网、行业资讯站、论坛、自媒体、权威媒体等完整内部能力。如果仅靠前端隐藏,合伙人仍可能通过接口看到隐藏交付能力。

目标改造:

- 合伙人套餐、客户套餐、项目配额、项目详情使用合伙人专用 DTO。
- 后端响应中不返回行业资讯站、论坛/平台网站、权威媒体、指纹浏览器、自媒体账号绑定、本地助手等字段。
- 总部接口保留完整配置和快照。

### 19.7 页面缺口

当前合伙人门户只有首页、客户、项目、余额、培训。需要新增:

- 客户套餐绑定。
- 项目启动申请。
- 核心问题专页。
- 合伙人诊断报告。
- 合伙人员工管理。

总部需要新增:

- 合伙人套餐管理。
- 合伙人积分管理增强。
- 项目启动审批。
- 总部配置准备看板。
- 审批快照和套餐快照查看。

### 19.8 可复用基础

建议复用:

- `partner`、`partner_account`、`partner_account_txn`、`partner_recharge_order`。
- `company_package_binding`。
- `project_channel_allocation`。
- `company.owner_id` 作为总部内部交付负责人分配。
- 现有权限表、活动日志、文件存储能力。

需要新增或扩展:

- 合伙人套餐可见性和上下架。
- 合伙人员工客户级分配。
- 项目启动申请/审批。
- 项目配额占用和锁定快照。
- 积分凭证和审批关联。
- 合伙人专用 DTO/API。
- 诊断报告 `partner_id` 归属、免费次数、超额积分消耗。
- 客户内部交付负责人移交流程和审计。

客户移交需要优先复用现有 `/api/companies/{id}/owner-transfer` 能力和 `delivery.assignment.manage` 权限;若新增 `/api/admin/companies/{id}/owner-transfer` 包装接口,必须保持同一套服务和审计逻辑。若管理者也允许移交,需要同步调整权限种子和断言。
